# OpenAI API 연동 검토

작성·공식 문서 확인: **2026-11-10, Asia/Seoul**. 상태: **제안 / 구현·유료 호출·계정 설정 미착수**.

현재 Miruvor는 기기 안의 SQLite와 사진 파일로 동작하는 앱. P1의 와인·구매·병 분리와 DB v2 보존 구현은 완료; AI 호출, API 서버, API 키 관리 기능은 아직 없음. 이 문서는 [프로젝트 계획](project-plan.md)의 선택적 외부 연동 검토이며 API 기능의 구현 완료를 의미하지 않는 자료.

## 권장 기능과 순서

제품 목표인 적은 입력, 개인 경험 보존, 재구매 판단에 기여하는 순서.

| 순위 | 기능 | 사용자에게 주는 가치 | 저장 원칙 / 착수 시점 |
|---|---|---|---|
| 1 | 라벨 사진 → 와인 입력 초안 | 긴 외국어 이름·생산자·빈티지 입력 부담 감소 | 보이는 정보만 제안, 사용자 확인 후 저장; P1 구조에 맞춰 P2 입력 흐름에 연결 |
| 2 | 한 줄 시음 메모 → 항목 정리 | 감상을 향·맛·페어링으로 나누는 수고 감소 | 원문 보존, 언급하지 않은 맛·평점·재구매 의사는 비워 두기; P2 이후 |
| 3 | 내 기록을 근거로 한 자연어 검색·회고 | “지난번에 마신, 산도가 좋았던 화이트” 같은 기억 회수 | 로컬 기록에서 후보 검색 후 근거 노트로 연결; 기록이 쌓인 뒤 |
| 보류 | 영수증·가격표 인식 | 구매 수량·가격·판매처 입력 보조 | 할인·세트·병당/전체 가격 혼동 검증 필요; 라벨 실험 다음 후보 |
| 보류 | 일반 와인 추천·현재 시세 답변 | 새로운 와인 탐색·가격 참고 | 실제 출처·시점·빈티지·용량 데이터 없이는 현재 가격 관측치로 저장 불가 |

추천 1차 범위: **라벨 한 장을 읽어 저장 전 초안을 만드는 기능**. 평가 대상이 눈에 보이는 사진이어서 정답 확인이 가능하고, 신규 사용자에게도 즉시 도움이 된다는 제품 판단. 추천·취향 분석은 기록이 쌓인 뒤 검토.

OpenAI의 이미지 입력은 사진 속 내용을 분석하는 기능이며, 이미지 자체도 토큰으로 과금되는 대상. 작은 글씨·기울어진 라벨 등은 인식 오류 검증 대상. [이미지 입력 공식 문서](https://developers.openai.com/api/docs/guides/images-vision).

## 1차 입력 흐름

```text
사용자가 선택한 라벨 사진
  → 필요한 부분 자르기·전송용 이미지 준비
  → 서버를 통해 Responses API 호출
  → 정해진 형식의 와인 초안 반환
  → 읽은 근거와 비어 있는 항목 확인·수정
  → 기존 와인 후보 선택 또는 새 와인 생성
  → 기존 로컬 저장 흐름으로 저장
```

- 추출 후보: 제품명, 생산자, 빈티지 구분/연도, 국가·지역, 종류, 품종, 용량.
- 라벨에 없거나 읽기 어려운 항목은 null. 라벨에 연도가 보이지 않는다는 이유로 NV로 확정하지 않는 규칙.
- 와인 종류·품종도 보이는 표기 근거를 우선. 모델의 일반 지식으로 빈칸을 조용히 채우지 않는 범위.
- 용량은 Wine의 동일성 필드가 아니므로 초안의 별도 항목으로 유지하고, 구매·병 생성 시에만 해당 기록에 반영.
- 값과 함께 근거가 된 라벨 문구, 확인 필요 여부를 반환. 모델이 말한 확신 수치를 검증된 정확도로 표시하지 않는 원칙.
- JSON Schema 기반 Structured Outputs 사용 후보. 형식 준수가 내용의 정확성을 보장하지 않으므로 값 검증과 사용자 확인은 별도 단계. [구조화 출력 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs).
- 원본 사진은 기기에 보존. API 전송은 사용자가 인식을 선택한 사진에 한정하고 전송 사실을 표시.
- 전송용 파생 이미지는 지원 형식으로 준비. HEIC 등은 JPEG/PNG로 변환하고 원본 파일은 유지. [지원 이미지 형식](https://developers.openai.com/api/docs/guides/images-vision).
- 거절·시간 초과·크레딧 부족·오프라인일 때도 사진과 수동 입력을 저장할 수 있는 흐름.
- AI 응답이 DB ID를 정하거나 기존 와인을 자동 병합하지 않는 구조. 관계·미상 값·사진 보존은 [P0 정책](domain-policy.md) 준수.

시음 메모 정리도 같은 초안 원칙 적용. 예를 들어 “체리 향, 산도가 좋아서 다시 사고 싶음”의 표현을 해당 항목에 옮기되, 사용자가 쓰지 않은 4점 평점·타닌 수치·음용 적기 등은 생성하지 않는 범위.

## 앱과 서버의 역할

권장 구조: Flutter의 선택적 입력 보조 화면 → 작은 중계 서버 → OpenAI API → 초안 → 사용자의 로컬 저장.

- 앱: 원본 기록·사진, 사용자 확인, 수동 입력, 로컬 저장 담당.
- 서버: API 키 보관, 요청 인증, 크기·횟수·출력 한도, 재시도 제한, 사용량·비용 집계 담당.
- 개발용 개인 실험은 로컬 실행 환경의 프로젝트 키로 가능. 배포 앱은 서버의 프로젝트 서비스 계정 사용을 검토.
- API 키를 Flutter 코드·앱 배포 파일·로그에 포함하지 않는 기준. 공식 문서도 모바일 앱에서 비밀 키를 노출하지 않고 서버에 보관하도록 안내. [API 키와 서비스 계정](https://developers.openai.com/api/docs/guides/api-keys).
- 인증 없는 공개 중계 주소는 배포하지 않는 기준. 전체 앱 계정·동기화를 먼저 요구하지 않더라도 API 호출 경로의 접근 통제는 필요.
- 기본 기록 기능에는 서버 연결을 요구하지 않는 구조. 동기화 서비스와 AI 입력 보조는 서로 독립적인 후속 기능.
- 서버의 원문·사진 로그는 기본적으로 남기지 않는 제안. 외부 제공자의 데이터 보관 조건과 전송 안내 문구는 실제 연동 전에 확인할 항목.

서버 운영비와 API 사용료는 별개. API 크레딧으로 서버 호스팅 비용까지 충당되는 것으로 계산하지 않는 기준.

## 구독 API 크레딧 확인 사항

공식 안내 기준, 해당 혜택은 연결한 API 조직의 Responses 이미지 이해·텍스트 처리 등에 사용 가능. 구독 청구 주기 말에 미사용분 만료, 이월 없음. 첫 지급은 남은 기간에 따라 비례 산정될 수 있고, 자격과 혜택 유지 시 갱신에 맞춰 재지급되는 방식. [ChatGPT 구독 API 크레딧](https://developers.openai.com/api/docs/guides/chatgpt-api-credits).

- 이 검토에서는 사용자가 받은 약 $100를 실험 예산의 배경으로 사용. 실제 계정의 지급액·잔액·만료일·연결 조직은 조회하지 않은 상태.
- 호출에 사용할 키는 크레딧을 받은 조직의 프로젝트에 소속되어야 하는 조건.
- 혜택은 ChatGPT·로그인한 Codex의 사용 한도를 늘리지 않으며, API 키로 이용하는 Codex 사용에는 적용되지 않는 조건.
- 무료 크레딧 소진 후 구매한 크레딧이 남아 있으면 계속 차감, 남은 크레딧이 없으면 요청 실패. [적용 범위와 소진 시 동작](https://developers.openai.com/api/docs/guides/chatgpt-api-credits).

## 모델과 비용 가설

첫 비교 후보: **GPT-5.4 mini**. 공식 모델 문서상 이미지 입력, Responses API, Structured Outputs 지원. 특정 모델의 정확도나 최저 비용 우위를 아직 실험으로 확인하지 않은 상태이며, 최종 선택은 아래 평가 결과를 기준으로 결정.

공식 Standard 가격: 입력 100만 토큰당 **$0.75**, 출력 100만 토큰당 **$4.50**. [GPT-5.4 mini 지원 기능·가격](https://developers.openai.com/api/docs/models/gpt-5.4-mini).

예시 가정: 요청당 과금 입력 2,000토큰(이미지 환산 포함) + 과금 출력 300토큰, 추론 `none`, 캐시 할인·별도 도구 비용 없음.

```text
1회 = 2,000 × $0.75 / 1,000,000 + 300 × $4.50 / 1,000,000
    = $0.00285
1,000회 = $2.85
```

실측 견적이 아닌 가정 계산. 사진 크기·상세도, 출력 길이, 실패 후 재시도, 모델 선택에 따라 달라지는 비용. $100 전체를 소진하는 목표 대신 소액으로 정확도와 입력 시간 개선부터 확인하는 제안.

## 제안 실험과 통과 조건

라벨 품질 실험은 앱 구조 변경과 독립적으로 준비 가능. P1 완료 후 별도 후속 작업으로 실제 앱 연결을 검토. 이번 P1 구현에는 실험 실행·API 호출·지출을 포함하지 않은 상태.

1. 사용 권한이 있는 라벨 사진 30~50장과 사람이 확인한 정답 준비. 선명한 사진, 반사광, 작은 글씨, 연도 미상, NV, 같은 제품의 다른 빈티지 포함.
2. 비용 **$5 이내**를 1차 실험 목표로 설정. 호출 수·출력 길이·재시도를 제한하고 예산 도달 전 중단할 장치 준비.
3. 제품명·생산자·빈티지의 정확 일치율, 근거 없는 값 채움, 사람이 고친 필드 수 기록.
4. 수동 입력 대비 확인·수정을 포함한 저장 시간, 응답 대기 시간, 실제 토큰과 요청당 비용 측정.
5. 미상 빈티지를 NV나 임의 연도로 채우는 사례, 자동 병합, 확인 없는 저장은 차단.
6. 오류·거절·연결 끊김에서도 원본 사진과 수동 저장이 유지되는지 확인.

초기 통과 목표: 검증 사진의 읽을 수 있는 핵심 필드 정확도 90% 이상, 사용자 확인을 포함한 중앙 저장 시간 30초 이내이면서 수동 입력보다 짧을 것. 각각 필드 수·사진 수와 함께 결과 기록. 읽을 수 없는 필드의 임의 채움은 별도 오류로 집계하고 사용자 확인 없이 반영되는 사례는 0건이어야 하는 기준.

최종 모델, 서버 방식, 초안 필드 스키마, 배포 대상과 실제 예산 집행은 실험 착수 시 결정. P1 완료는 데이터 분리·보존과 자동 검증 범위이며 API 착수는 별도 작업.
